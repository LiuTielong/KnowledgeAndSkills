# 推理框架与系统实现

## 1. 为什么需要推理框架

模型架构和权重定义了如何从输入 token 计算输出 logits。借助 PyTorch 等计算框架，再配合采样和生成循环，就可以实现基本的文本生成。

当模型部署在服务器上，为多个用户持续提供服务时，还需要解决请求、显存和计算资源的组织问题。推理框架为这些工作提供统一的运行机制，其作用主要可以归纳为三点：请求调度、运行时状态管理，以及高效地执行模型计算。

### 1.1 请求调度

不同请求在不同时间到达，输入长度不同，实际生成长度通常也无法提前确定。系统需要决定哪些请求进入执行、每轮处理多少 token，以及如何安排 Prefill 和 Decode。

这些选择会影响首 token 延迟、生成过程中的停顿和整体吞吐。例如，扩大执行批次可能提高整体吞吐，也可能增加单个请求的等待时间。框架需要根据服务目标，在这些指标之间进行取舍。

### 1.2 运行时状态管理

每个请求都有自己的生成进度和 KV Cache，上下文增长时，缓存也随之增长。如果直接按照最大上下文长度预留空间，会浪费显存并限制并发容量。因此，系统需要按需分配、复用和回收缓存，同时维护请求状态、采样状态等运行时信息。

PagedAttention 是缓存管理优化的代表：通过分页存储和配套的注意力计算，减少预留与碎片造成的浪费；在相同表示格式下，它不改变每个 token 的 KV 数据量。这与 MLA、KV 量化等减少缓存表示大小的方法属于不同的优化方向。[参考：PagedAttention 原论文](https://arxiv.org/abs/2309.06180)

### 1.3 高效地执行模型计算

在多卡环境中，系统要组织参数和任务的分布、设备之间的通信，以及计算与通信的配合；在单张 GPU 内，也需要选择适合模型和硬件的算子与执行方式。

请求调度、缓存布局和计算内核之间存在依赖，需要共同设计。例如，分页存储 KV 后，Attention 内核也需要支持根据块映射读取历史数据，才能在这种存储布局上完成正确的计算。

推理框架将模型计算、动态请求和硬件资源组织成一个持续运行的系统，在正确执行模型与生成策略的前提下，提高资源利用率，并满足服务对吞吐和延迟的要求。在八卡 RTX PRO 5000 上使用 DeepInfer 为同事提供 DeepSeek 服务，就是这些工作的一个实际场景。
